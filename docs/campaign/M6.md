# M6: existing job SDK and optimization studies

The separate `integrations/jobs` workspace pins fcmaes-rust 583f33a and its
actual optimization-job-api revision 602d31a. The then-current runner tested
is optimization-jobs cc6b03d. The default numerical workspace has no job SDK,
optimizer or Rayon dependency. No new envelope or lifecycle was invented.

The native worker registers `app.crn.fit-moments` and `app.crn.circuit-score`
with existing retry, surrogate and evaluate profiles. Inputs are hashed model
and fit-data files; rate coordinates are natural logarithms. Fit loss uses
normalized mean/variance time-course residuals. Circuit score adds a per-path
amplitude-floor penalty to the fixed-topology temporal-shape loss. It is an
explicit synthetic calibration objective, not a biological oscillation certificate.
Actual three-gene example data and model are included under integrations/jobs/examples.

Every candidate uses the same declared seed_set and replicate streams; the
point-derived SDK seed is intentionally unused. Incomplete work fails the
objective. A checkpoint bridges SDK cancellation/deadline to the event loop,
and the numerical worker count is at most the supplied thread allowance.

`validation/check_jobs.py` executes the real worker through optimization-run:
15 optimization/evaluate jobs plus a shell-free command job, an active deadline,
32-call equal-budget BiteOpt versus surrogate at 8 and 64 replicates, SDK rechecks,
separate disjoint-seed best-point validation jobs, 1/8-thread equality, explicit
failure accounting and ring/broken-ring held-out evaluations. Reports preserve
native manifests and search versus validation work. This is a small pilot, not
a ranking of search algorithms or a guarantee of fit identifiability.

Early driver failures (a discovery example assumed per model/profile, and a
wrong surrogate budget field) are retained. The final driver uses the actual
SDK discovery shapes and `evaluations` field. Initial clippy suggestions were fixed.

Build: `cargo build --release --locked --manifest-path integrations/jobs/Cargo.toml`.
Register the resulting crn-job-worker with the existing runner, or use its
`describe`, `validate` and `execute` commands. Publishing remains owner-controlled.
